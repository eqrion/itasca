# Lean port plan

This is the historical Rocq-to-Lean port plan. The later
[streaming consolidation](STREAMING_PROOF_PLAN.md) made `validate_streaming` the
sole module driver, preserved ordinary whole-module guarantees, and retired the
old module/code visitor APIs and their deferred/module-trace contracts. Current
claims are in the [public guarantees](README.md#formal-verification) and
[guarantee comparison](lean/PARITY.md); the plan and checkpoints below describe
their original revisions.

Port itasca's verification from Rocq to Lean while retaining the Rust validator's
Wasm 1.0 behavior and public interfaces. The specification target is the Wasm 1.0
subset of the Wasm 2.0 definitions generated by SpecTec. Full Wasm 2.0 support is
a subsequent project.

The migration was developed on `lean-port`, initially beside the Rocq theories.
This file retains the original plan and dated checkpoints. The current workflow
and public guarantees are in [README.md](README.md) and
[DEVELOPMENT.md](DEVELOPMENT.md).

The final review preserves the old `main` commit under the annotated
`rocq-baseline` tag and makes this branch Lean-only. Rocq theories, dependencies,
patches and build commands are removed from the active tree; `main` remains at
the baseline pending user review of the migration commit.

Whole-module soundness, declarative completeness and decomposed/visitor/deferred/
separate-buffer guarantees are checked, including accepted module callbacks.
The [comparison](lean/PARITY.md) records consumer coverage and exact hypothesis
differences rather than claiming literal parity for every auxiliary theorem.
The [final validation record](lean/baseline/VALIDATION.md) records clean project
proof rebuilding, tests and reproducible extraction. Production Rust behavior
is unchanged; three unit-test macro qualifications enable the no-default-feature
test suite. [UPSTREAM.md](UPSTREAM.md) tracks the source fixes and investigations.

## Decisions

- Keep Rust behavior unchanged during the initial compatibility work. The current
  extraction restrictions remain in force until changes are verified with the
  new backend.
- Try a clean, newer Aeneas version with its matching Charon revision and Lean
  library. Do not carry the Rocq extraction patches into the Lean build by
  default. Retain the existing Aeneas checkout for the Rocq baseline while
  evaluating the new toolchain separately.
- Vendor the full SpecTec repository at an exact commit from `lean-backend` so
  fixes can be made to the specification or generator and contributed upstream.
  Record regeneration commands and toolchain versions.
- Keep generated definitions separate from handwritten proofs and adapters.
  Fix generators, or use explicit versioned source patches; do not silently edit
  generated definitions to make proofs pass.
- Target the generated declarative typing judgments. A second executable
  validator is optional. Introduce a local algorithmic proof layer only if the
  representative proof shows a clear benefit, and prove its correspondence with
  the generated judgments.
- Retain the handwritten binary specification initially. Generated typing
  judgments alone do not establish what the input bytes encode.
- Preserve implementation limits and all visitor, streaming, and deferred
  validation guarantees. Do not introduce extra restrictions to avoid valid
  Wasm 1.0 cases that expose upstream specification bugs.

## Correctness targets

The theorem inventory in [README.md](README.md#formal-verification) is the
acceptance checklist. Port statements and their hypotheses deliberately rather
than measuring progress by the number of translated files.

At the whole-module level, establish:

1. Every input terminates without modeled panic, subject to the existing
   allocation assumptions.
2. Acceptance implies that the bytes represent a module in the supported
   Wasm 1.0 profile and that the generated module typing judgment holds.
3. Reported import and export types correspond to the decoded module.
4. Every valid supported module within the implementation limits is accepted.

The existing module completeness result is stated against WasmCert's executable
checker, whose module-level completeness is not proved there. The Lean port must
make its completeness target explicit; completeness against generated declarative
typing would strengthen the result.

Define the Wasm 1.0 profile together with the binary representation relation.
The existing `module_1_0` predicate has only three clauses because other
restrictions are already carried by the binary specification. Account for value
types, instructions, function and block types, tables, segments, and encodings.
Check semantic differences between specification versions rather than assuming
that a syntax restriction alone establishes equivalence.

For function bodies and decomposed module APIs, preserve context agreement,
opcode trace accuracy, visitor rejection behavior, entry validation, deferred
validation, and composition of separate buffers. These are part of the port,
not optional follow-up work.

## Milestones

### 1 Reproducible compatibility baseline

- Record the Rust revision, dependency pins, current tests, proof build, and
  transitive assumptions of the existing theorems.
- Build a clean Aeneas and its matching Charon; extract all current Rust to Lean.
- Compile the extracted implementation and pinned SpecTec definitions using one
  compatible Lean toolchain.
- Reproduce SpecTec generation from source and distinguish generated output
  from the checkpoint's handwritten additions.
- Inventory missing external models and upstream specification or generator
  defects with small reproducible examples.

Exit condition: both models compile together, the generation process is
repeatable, and remaining blockers are concrete and recorded.

### 2 Representative control flow proof

Prove a path through byte decoding, numeric instructions, nested control flow,
branches, unreachable stack polymorphism, and a visitor. Relate the extracted
Rust state to the generated instruction typing judgments and establish
termination for the chosen path.

Start with a direct declarative invariant, reusing the ideas behind the existing
ghost instruction lists and control frames. Evaluate whether a small pure stack
transition layer would simplify completeness. Any such layer needs proved
soundness and completeness, not axiomatized correspondence.

Exit condition: a representative correctness proof with audited dependencies and
an informed architecture decision before scaling to all instructions.

### 3 Foundations and binary representation

Port scalar bounds, collections, loop arguments, readers, signed and unsigned
LEB128, floating-point bit representations, type translations, and byte-format
relations. Prove necessary well-formedness facts about generated spec types.
Prefer existing proved Aeneas models over the old handwritten Rocq axioms.

Exit condition: reusable foundations and explicit Wasm 1.0 correctness statements.

### 4 Function bodies

Complete all instruction families and structured control. Establish body
soundness, completeness, termination, visitor trace correctness, and correct
opcode-to-hook dispatch.

Exit condition: the body API has equivalent guarantees to the Rocq version.

### 5 Modules and consumers

Port environment and section decoding, constant expressions, code entries,
imports and exports, and whole-module correctness. Finish visitor overrides,
deferred function validation, and separate-buffer composition.

Exit condition: every documented public theorem has a Lean counterpart with
reviewed hypotheses and no unexplained weakening.

### 6 Audit and default pipeline

Require reproducible extraction, Rust and specification tests, theorem parity,
and transitive Lean assumption checks before changing the default proof build.
Document trust-base changes and tag the working Rocq baseline before retiring
it. The recorded pre-port revision is `e7a6ce602de0716de89f955300f711b23bc1403e`;
verify the tag preserves the source, dependency pins, patches, and build
instructions needed to reproduce that baseline. Then make the default build
Lean, remove Rocq-specific files and dependencies, and carry the completed port
onto `main`.

## Trust and upstream work

No new project axiom, `sorry` proof, or kernel bypass may be used to work around
a missing proof. Audit exported Lean theorems with `#print axioms`; reject
`sorryAx` and explain any domain-specific assumptions. Standard Lean logical
axioms and modeled platform assumptions should be distinguished from missing
proofs. Track exact assumptions rather than comparing counts across provers.

The upstream checkpoint contains unfinished lemmas and opaque numeric models.
Determine which declarations are actually needed by validator correctness.
Completing upstream execution preservation and progress is not a prerequisite,
but an incorrect typing definition that excludes a valid Wasm 1.0 program is a
blocker for the corresponding validator theorem.

Kernel checking and axiom audits do not establish that a generated definition
faithfully represents the specification. Preserve provenance and regression
examples for immutable globals, imports, control flow, and malformed encodings.

For an upstream issue: minimize the example, locate the responsible specification
rule or transformation, add a regression test, fix that source, regenerate, and
rerun the affected proofs. Keep fixes in reviewable upstream commits or explicit
source patches until they are accepted. Filing issues and publishing fixes are
separate actions from preparing them locally.

## Iteration and parallel work

During the initial port, Rocq served as the reference while Lean-only iterations
used targeted Lean builds and the saved Rocq assumption report. Shared Rust
changes then required both pipelines. With Rocq now archived, the active policy
is [AGENTS.md](AGENTS.md#before-saying-you-are-done): build the changed Lean
module during iteration and run `just prove` with its axiom audit at integration;
Rust changes require Lean regeneration and the Rust tests.

The next whole-module milestone can be divided among three workers and an
integrator. Agree on the raw syntax, binary relation, elaboration, and environment
invariants first; the tracks below depend on those shared contracts.

| Track | Ownership and initial work | Dependencies |
| --- | --- | --- |
| Binary and framing | New module binary/reader files: vectors, names and UTF-8, primitive types, section framing, byte spans and slice rebasing | Existing LEB/float readers and `Wasm.BytesAt`; source UTF-8 correction for generated name well-formedness |
| Environment and declarations | Environment decoder, constant expressions, imports/exports, globals, tables/memories, elements/start; cache coherence and index bounds | Binary helper contracts and canonical import projections; can prove semantic assembly lemmas before decoder bridges |
| Functions and code | Grouped locals, code entries and section tiling, body-context transport, accepted-body Wasm 1.0 profile, `on_function_start` | Existing body theorems; raw code syntax, local bounds and environment-coherence contracts |
| Integration and tail | Shared module definitions, SpecTec fixes/adapters, data/tail decoder, public module composition, external-type accessors, `Audit.lean` and build files | Constant-expression helpers and the other tracks' proved contracts |

Agree on shared definitions and theorem statements before dependent work starts.
Keep file ownership distinct; serialize changes to generated sources, shared
definitions, and build configuration. Workers check their modules and publish
compiled dependencies at agreed checkpoints. Coordinate these target builds:
dependent checks can temporarily see missing artifacts while Lake rebuilds a
shared dependency. The integrator runs the combined build and audit. Missing dependencies stay explicit
in the work plan rather than becoming axioms or admitted lemmas. The binary and
environment tracks supply dependencies to the other tracks, so this is not
three fully independent ports or a promise of a threefold speedup.

## Initial evidence

Progress is recorded in [lean/README.md](lean/README.md). The Rocq baseline
passes. The full Rust crate now extracts and compiles together with freshly
regenerated SpecTec definitions on the shared Lean toolchain. Local source
patches address the Aeneas compatibility failures and preserve both global
mutabilities in SpecTec output; their scope and regression cases are in
[lean/upstream/](lean/upstream/README.md).

The representative core-profile checkpoint is retained in
`Itasca/CoreSoundness.lean`. The full body milestone now extends the actual
extracted `validate_body` and `validate_body_with` APIs to **every Wasm 1.0
instruction and every input byte sequence**, removing `Core.Profile` and
valid-immediate premises. `Itasca/WasmSoundness.lean` establishes termination
and acceptance soundness; `VisitorBodyErasure.lean` removes hook termination
from the acceptance theorem. Termination of the visiting API still requires
terminating hooks.

The direct declarative architecture scales: `Sequence.TypedPrefix` and
`WasmFrames` retain active and suspended typing derivations, while `Wasm.State`
records the bytes consumed so far. Reader errors therefore need no valid-token
assumption about the remaining input. The dispatcher proof covers numeric and
memory maps, environment-dependent operations, branch tables, control flow, and
unsupported bytes. No executable SpecTec checker or extra axiom is required.

The body context now translates the actual stored environment tables, including
cached direct-call signatures. Soundness is stated for zero-or-one function
results, preserving Wasm 1.0 behavior; termination also handles arbitrary result
vectors exactly as the implementation does. This does not prove that module
parsing constructs coherent environment caches.

`Itasca/WasmComplete.lean` now proves completeness of the actual public
`validate_body` directly from independent byte encoding and generated
`Instrs_ok`, within the body size cap and the Wasm 1.0 signature restrictions.
`DeclarativeComplete` normalizes sequence, framing, and subtyping derivations;
forward stack and handler proofs force successful dispatch. `StructuredProgram`
and `CompletenessProgram` compose actual executions by induction on token length,
including both arms of an if, and `BodyProgramComplete` closes the final frame
and discharges the public guards. No executable specification checker or
abstract execution premise remains in the public theorem.

`VisitorBodyComplete` lifts this result to `validate_body_with` when every hook
terminates and accepts. Its stronger `accepted_lift` theorem transfers arbitrary
accepted non-visiting bodies, without a result-shape or valid-body premise.
`FullVisitorAccept` covers all 174 hooks; `VisitorComplete` transfers successful
actual steps, including the callbacks inside branch-table label decoding.
Together with acceptance erasure, this preserves the two APIs' acceptance
behavior for non-rejecting consumers. The trace milestone below additionally
identifies the observed callbacks.

Completeness exposed a real specification-version difference. The Wasm 1.0
`br_table` rule requires identical target signatures; Wasm 2.0 permits a common
subtype, including `BOT` below different numeric targets in unreachable code.
Restricting only the opcode and value-type syntax therefore does not recover
Wasm 1.0 validity. `Wasm1Profile` adds an independent recursive target-equality
condition. `WasmCompletenessBoundary.validated_but_rejected` proves that a concrete
11-byte body has generated Wasm 2.0 typing but is rejected by the actual validator
with `TypeMismatch`. This is expected version behavior, not a generator defect;
no upstream patch or implementation change is needed.

`VisitorBodyTrace` now closes the body visitor trace milestone. All 174 callback
identities and their raw arguments have a common recording contract; independent
mnemonic maps check numeric and memory dispatch. Every ordinary returned body
run has a trace of complete byte-encoded instruction chunks, possibly followed
by a partial branch-table vector on error. Rejected hooks remain in the trace,
and no callback follows an observed rejection. Label callbacks precede target
merging, so even the label that causes a type mismatch is retained. The table's
default target is not reported as a vector-entry callback.

Accepted traces spell the same generated SpecTec-typed body as acceptance
soundness. `WasmBinaryUnique` aligns the syntax witnesses using independent
binary determinism. The always-accepting recorder has termination and
completeness theorems; a general instrumentation wrapper preserves ordinary
results and underlying visitor state in both directions, including rejection.
The body API emits no function-start callback. Kernel-checked public regressions
exercise nested control, exact float bits, partial label decoding, callback
rejection, and final-end-before-trailing-bytes behavior.

## Whole-module soundness milestone

The 2026-10-05 module assessment expands the next task beyond code entries.
The target is the actual extracted public `validate_module`, from arbitrary
bytes through environment, code, and tail validation. Establish three public
guarantees together:

1. Every byte sequence returns an ordinary success/error result without modeled
   panic or divergence. The module size guard and decoder establish the bounds
   needed by lower-level APIs; callers supply no environment-validity premise.
2. Acceptance gives an independently decoded module, matching returned metadata,
   generated SpecTec `Module_ok`, and the additional Wasm 1.0 conditions below.
3. The actual `import_types` and `export_types` accessors succeed and report the
   types of that same module, in declaration order.

The Rocq comparison includes `Module_NoPanic.v`, `Spec_Module.v`,
`Module_Sound.v`, and the final `validate_module_typed` theorem in
`Module_Typing.v`. Porting only `Module_Sound.v` would leave declarative typing
and the external-type guarantee unfinished. Lean will construct `Module_ok`
directly; an executable SpecTec validator is not a prerequisite.

### Shared representation and proof contracts

Use an independent raw module syntax and binary relation, followed by semantic
elaboration into the generated SpecTec module. Raw imports retain function type
indices; generated imports contain expanded external types. Raw code entries
retain grouped local declarations and body syntax; Rust's returned `Module`
retains only environment and tail metadata. Preserve these distinctions instead
of reconstructing an arbitrary typed module unrelated to the original bytes.

The soundness conclusion will have the following shape (names are provisional):

```text
validate_module bytes = success decoded
  → ∃ raw spec,
      ModuleBinary bytes raw
      ∧ Represents decoded raw
      ∧ Elaborates raw spec
      ∧ Module_ok spec
      ∧ Wasm1.ModuleConditions raw spec
```

`ModuleBinary`, `Elaborates`, and `Wasm1.ModuleConditions` must be independent
of validator acceptance. Define canonical import projections and resolved index
spaces explicitly. Prove cached function signatures equal resolution of imported
function type indices followed by defined function type indices; all lookups
must be in range. Prove imported counters and global/table/memory caches match
imports followed by definitions. Keep length equalities alongside the generated
`Forall₂` relations, whose implementation uses `zip`.

Initializers use only imported immutable globals. Function bodies use the full
global index space, parameters followed by declared locals, and the resolved
result signature. Prove transport from the current body context's empty
`ELEMS`/`DATAS` fields to the populated module fields. Prove constant-expression
typing, constant-i32 element/data offsets, element function-index bounds, and
the elaboration of legacy element indices to generated `REF_FUNC` initializers.

The binary layer must account for the header, optional ordered sections, custom
sections, exact section/entry lengths, vector counts, supported nonminimal LEB
encodings, UTF-8 names, copied payloads, and complete input consumption. Code
entries must exactly tile the code section, with a validated body for every
declared function. Reuse the existing body and reader proofs rather than adding
an abstract assumption that successful entry validation implies typing.

### Specification prerequisites and preserved conditions

The pinned source/output review found concrete gaps to handle before claiming
the full result:

- **UTF-8 source defect:** `specification/wasm-2.0/A-binary.spectec` bounds the
  four-byte case below `U+11000`, rather than `U+110000`. Consequently generated
  name well-formedness excludes valid accepted names such as U+1F600. Correct
  the source in a reproducible local patch, regenerate, and add boundary and
  emoji regressions. An otherwise empty module importing an immutable i32
  global with an emoji import name is a small end-to-end fixture. Do not narrow
  the API to ASCII or interpret UTF-8 bytes as individual Unicode characters.
- **Import projections lose `otherwise` guards:** generated `fun_funcsxt`,
  `fun_globalsxt`, `fun_tablesxt`, and `fun_memsxt` have unrestricted fallback
  cases that can discard matching imports. Correct forward witnesses remain
  possible. Establish exact canonical projections and cache equalities
  independently; never use these relations alone to infer coherence. Prepare
  a minimal reproducer and a source/backend fix or explicit local workaround.
  The public result must retain canonical import spaces even if the upstream
  relation remains weaker.
- **Missing module conditions:** the source has a TODO for distinct export
  names, and generated `Module_ok` bounds only defined memories. Separately
  prove unique decoded export names and the Wasm 1.0 limits on total imported
  plus defined tables/memories. Connect Rust's bytewise duplicate check to
  decoded-name uniqueness by proving that equal decoded names have equal valid
  UTF-8 byte encodings. Include numeric types, supported segment forms,
  and zero-or-one function results in the independent profile.
- **Body profile soundness:** current accepted-body theorems supply independent
  Wasm 1.0 bytes and generated Wasm 2.0 typing; they do not yet conclude the
  recursive `Wasm1.Instructions` target-equality profile used by completeness.
  Prove accepted bodies satisfy that condition, using successful branch-table
  target merging and structured-body composition. Completeness cannot supply
  its converse. This is required before describing the module result as the
  full Wasm 1.0 semantic profile.

Source fixes must preserve generation provenance and pass `spec-check` and the
integrated Lean audit. Prepare upstream reports locally; publishing them is a
separate action. Keep every unresolved defect explicit in the milestone status.

### Delivery order and exit criteria

First land the shared raw syntax/contracts and minimized SpecTec regressions.
Then run the three worker tracks above alongside integration and tail work,
checking each dependency at agreed checkpoints. Compose public soundness,
termination, and import/export correspondence only after those contracts are
discharged by actual decoder proofs.

Kernel-checked module regressions should exercise an empty module, imported and
defined functions with locals/calls, immutable imported globals and constant
initializers, exports/start, active element/data segments, Unicode names, and
custom sections. Include malformed sizes/counts, duplicate exports, invalid
indices, and truncated code entries. Check the byte-to-module witness as well
as the final judgment; a theorem only about a hand-built `Env` is insufficient.

Exit requires the three public guarantees above, accepted-body/profile
alignment, source regeneration checks for any SpecTec changes, `just lean-prove`,
and an audit with no `sorryAx`, project axioms, or kernel bypasses. No abstract
parser, cache-coherence, or code-entry-validation premise may remain on the
default public API. Document the exact specification/profile guarantees and
remaining upstream weaknesses.

After this milestone, prove module completeness and complete the consumer APIs.
For `validate_module_with`, custom-section and need-bytes hooks can only reject,
but an overridden `CodeVisitor.on_code_entry` replaces body validation. Its
soundness theorem necessarily requires acceptance to certify validation of each
entry; hook termination is a separate requirement for totality. Deferred and
separate-buffer proofs must discharge those entry obligations and preserve byte
provenance. Full module callback traces are also subsequent consumer work.
These follow-ups remain required for Rocq parity, but do not gate this larger
default-API soundness milestone. Keep the Rust implementation and Rocq baseline
unchanged unless a demonstrated implementation defect requires a separate fix.

## Later Wasm 2 work

The 2026-10-06 final migration review is recorded in
[lean/baseline/VALIDATION.md](lean/baseline/VALIDATION.md). The old `main`
revision is tagged `rocq-baseline`; this branch now uses Lean-only default
commands and retains the source patches, upstream tracker and explicit
[guarantee comparison](lean/PARITY.md). The final `just verify` passes with
Rocq dependencies absent from the working tree.

After proof parity, extend the implementation and proofs by feature group:
sign extension and saturating conversions, multi-value, reference types and
multiple tables, bulk memory, and SIMD. Multi-value changes core control-stack
invariants; bulk memory changes module-validation dependencies. Prefer general
Lean lemmas where useful, without expanding the current Rust feature set during
the migration.
