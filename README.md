# itasca

***veritas caput***

A streaming WebAssembly decoder and validator written in Rust and verified
in Lean.

Validation supports WebAssembly Core 2.0, including streaming and parallel
function validation. Whole-module termination, soundness, and completeness are
proved.

This is an experiment in AI-assisted formal verification, built extensively
with Claude and Codex. Read [formal verification](#formal-verification) for
more details.

This file is written by a human, the rest of this repository is not.

## Usage

```rust
let bytes = b"\x00asm\x01\x00\x00\x00";
let module = itasca::validate_module(bytes)?;
let imports = module.import_types()?;
let exports = module.export_types()?;
```

The validator supports multi-value, sign extension, saturating conversions,
reference types, multiple tables, bulk memory, passive and declarative
segments, and SIMD instructions.

`validate_module` is internally implemented using the more powerful and complex
`validate_streaming` API. This API supports streaming reads, discontiguous
buffers, and parallel validation of function bodies.

```rust
use itasca::{
    Error, ModuleMetadata, Result, StreamingBatch, StreamingConfig, StreamingRegion,
    StreamingSource, StreamingVisitor,
};
use std::vec::Vec;

struct Input(&'static [u8]);
impl StreamingSource for Input {
    fn environment(&self) -> Result<&[u8]> { Ok(self.0) }
    fn code_len(&self) -> usize { 0 }
    fn code(&self, start: usize, end: usize) -> Result<&[u8]> {
        if start == 0 && end == 0 { Ok(&[]) } else { Err(Error::Host) }
    }
    fn tail(&self) -> Result<&[u8]> { Ok(&[]) }
}

struct Visitor<'a> { returned: Vec<StreamingBatch<'a>> }

impl itasca::ModuleVisitor for Visitor<'_> {}

impl<'a> StreamingVisitor<'a> for Visitor<'a> {
    fn custom_region(&mut self, _region: StreamingRegion) {}
    fn environment_ready(&mut self, _module: &ModuleMetadata) -> Result<StreamingConfig> {
        Ok(StreamingConfig { batch_bytes: 4096, max_batches: 2 })
    }
    fn submit_code_batch(&mut self, mut batch: StreamingBatch<'a>) -> Result<()> {
        // Implementations can synchronously validate a batch, or schedule it
        // for background validation. They must call `validate_func` on all
        // entries of the batch and eventually return it via `poll_code_batch`.
        let mut count = 0;
        while count < batch.len() {
            let entry = batch.next_entry()?;
            batch.validate_func(entry.index, &mut itasca::DefaultOpVisitor)?;
            count += 1;
        }
        self.returned.push(batch);
        Ok(())
    }
    fn poll_code_batch(&mut self) -> Result<StreamingBatch<'a>> {
        self.returned.pop().ok_or(Error::Host)
    }
    fn code_end(&mut self) -> Result<()> { Ok(()) }
}

let source = Input(b"\x00asm\x01\x00\x00\x00");
let module = itasca::validate_streaming(0, &source, &mut Visitor { returned: Vec::new() })?;
```

## Formal verification

The slice and streaming validators return module metadata with shared immutable code
descriptors and the decoded data segments. The soundness and completeness proofs cover
this returned metadata, including descriptor flags and ordered import and export types.

The pipeline is:

```text
Rust --Charon--> LLBC --Aeneas--> Lean program model
SpecTec Wasm 2.0 source ----------> Lean declarative judgments
Independent binary grammar ------> exact bytes and Wasm 2.0 instructions
Handwritten Lean proofs ----------> Itasca guarantees
```

“Accepts” means the extracted function returns ordinary `Ok`.
“Terminates” means it returns success or an error without panic, arithmetic overflow, out-of-bounds access, or divergence (allocation failure is not modeled).
“Well typed” refers to the generated SpecTec declarative judgments.
"Total" means that arbitrary bytes terminate.
"Sound" acceptance implies the bytes encode a module that is well typed.
"Complete" means that all well-typed binary encoded modules within implementation limits are accepted.

| Entry point | Guarantee |
| --- | --- |
| `validate_module` | Total, sound, and complete. |
| `validate_streaming` | Total under returning callbacks. Sound under coherent source views and issued-worker provenance. Complete for within-limit valid modules under readable canonical regions and an accepting scheduler that returns actual worker validation results in any order. |

### Trust boundary

The proofs depend on:
  1. Rust translation into Lean by Charon and Aeneas.
  2. Aeneas's standard-library and loop models.
  3. Validation judgments generated by SpecTec from pinned syntax and typing
     sources with [versioned patches](patches/).
  4. The [handwritten binary grammar](lean/WebAssembly/WebAssembly/Binary/Module.lean)
     and [external Rust operation models](lean/ItascaRust/ItascaRust/FunsExternal.lean).
     The shared-metadata model treats `Arc` construction, borrowing and strong-reference
     cloning as preserving the immutable value. It assumes successful allocation and
     a representable strong-reference count. Atomic memory ordering, destruction timing,
     and allocator and reference-count exhaustion are outside the model.
  5. The rustc compiler.
  6. Lean's kernel and standard logical foundations.
