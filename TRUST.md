# Trust

Generated by Opus 5.0, not human audited yet. Take with a grain of salt.

## Summary

itasca decodes and validates WebAssembly 1.0 module binaries in one streaming
pass. The Rust in `src/` is translated into Coq mechanically, by Charon and
Aeneas; the theorems in `theories/` are about that translated function. The
reference for "correct" is [WasmCert-Coq](https://github.com/WasmCert/WasmCert-Coq),
an independent formalisation of WebAssembly's type system.

Four things are proven about the whole-file entry point, in five theorems. It
always returns: no input makes it crash, overflow, or loop. If it accepts, the
input really is a Wasm 1.0 module binary, and the module that binary denotes
really is well typed by WebAssembly's own typing judgement. If WasmCert's module
type checker accepts a binary, itasca accepts it too, within stated size caps and
the three places Wasm 1.0 is narrower than the 2.0 type system WasmCert
formalises. The same four carry over to the decomposed entry points a compiler
drives itself, under two preconditions the caller owes.

Everything below is checkable. Every backticked name is a real theorem;
`just trust` prints the axioms behind each one, and `just prove` recompiles the
lot. The Coq blocks quoted here are the real statements with the extraction's
long field names shortened (`vm.(env)` for `vm.(module_Module_env)`, and so on),
so read them as faithful renderings rather than as text you can paste.

## Reading the statements

Three conventions carry most of the weight.

### What a theorem is about

Aeneas turns `fn f(..) -> Result<T, Error>` into a Coq function returning
`result (Result T Error)`. The outer `result` is Aeneas's, with two
constructors: `Ok x` for "returned normally", `Fail_ e` for "did not". Every way
a Rust function can fail to return an answer lands in `Fail_`: an out-of-bounds
index, an arithmetic overflow (Aeneas's scalars are refined integers, so
overflow is a failure and never a wraparound), a `Vec` that outgrew `usize`,
and, via the loop combinator below, a loop that never finishes. The inner
`Result` is itasca's own accept-or-reject verdict.

So `module_validate_module data = Ok (Ok m)` reads "returned, and the answer was
accept, with decoded module `m`", and a theorem shaped `exists r, f data = Ok r`
says `f` cannot do anything except return. Heap exhaustion is outside the model:
Aeneas's `Vec` never fails to allocate.

Aeneas leaves `usize_max` abstract, assuming only `u32::MAX <= usize_max`, so
every bound below is proven on a 32-bit host as well as a 64-bit one. That is
why `MAX_MODULE_BYTES` is 2^30: `Module_NoPanic.module_bytes_fits` derives
`2^30 + 65536 <= usize_max` from that one assumption, which is the headroom
every position and length bound in the crate is then argued from.

### Loops

Aeneas compiles every Rust loop into a call to a combinator

```coq
loop : (A -> result (LoopControl A B)) -> A -> result B
```

which this project supplies as an axiom constrained by a single equation,
`Aeneas_Specs.loop_unfold`:

```coq
loop f a = match f a with
           | Ok (Cont a') => loop f a'
           | Ok (Done b)  => Ok b
           | Fail_ e      => Fail_ e
           end
```

That equation is everything the proofs know about `loop`. It is satisfiable by
the intended reading, in which a diverging iteration is `Fail_`, so a Coq proof
of `exists r, loop f a = Ok r` has no choice but to bottom out at a `Done` after
finitely many unfoldings. That is why the no-panic theorems are also termination
theorems, and it is the exact sense of "never hangs": relative to the assumption
that `loop_unfold` faithfully models a Rust loop.

### The two directions

Soundness is "if it accepts, the input is good". Completeness is "if the input
is good, it accepts". Both are needed. Soundness alone is satisfied by a
validator that rejects everything; completeness alone by one that accepts
everything. Where they meet, the validator decides WasmCert's predicate, up to
the size caps and the Wasm 1.0 restrictions named below.

Both directions need a formal reading of "the input is good", and the two halves
come from different places. `repr_module` (in `theories/Spec_Module.v`) is a hand
transcription of the W3C binary format. It belongs to the trust base rather than
to the results, because WasmCert cannot supply it; see [The trust
base](#the-trust-base). `module_typing` and `module_type_checker` are
WasmCert's, unmodified.

## Part 1: `validate_module`

`validate_module` takes a `&[u8]` and returns `Result<Module, Error>`. It has no
preconditions at all: the size check is inside it.

### It always returns

```coq
Theorem validate_module_no_panic : forall data,
  exists r, module_validate_module data = Ok r.
```

For every byte string, including empty, truncated, random and adversarial ones.
No hypothesis. Together with the loop reading above, this rules out panics,
integer overflow, out-of-bounds indexing and non-termination, on any input.

### If it accepts, the input is a module binary

```coq
Theorem validate_module_repr : forall data vm,
  module_validate_module data = Ok (Ok vm) ->
  exists m, repr_module (byte_list data) m.
```

`repr_module` is spec 5.5.16's production read top to bottom: magic number,
version, then each section in id order with its custom-section padding, and it
consumes the whole file (its last premise leaves no bytes over). Section extents
come from size prefixes, so a section that under- or over-runs its frame is not
a reading. `Spec_Module.repr_module_det` proves a byte string has at most one
reading, which upgrades the existential to "the module": there is no second `m`
to worry about.

### If it accepts, the module is well typed

```coq
Theorem validate_module_typed : forall data vm,
  module_validate_module data = Ok (Ok vm) ->
  let env := vm.(env) in
  exists m imps exps,
    repr_module (byte_list data) m
    /\ module_import_types env = Ok (Ok imps)
    /\ module_export_types env = Ok (Ok exps)
    /\ mod_imports m = map translate_import env.(imports)
    /\ mod_exports m = map translate_export env.(exports)
    /\ module_typing m (translate_externtypes imps)
                       (translate_externtypes exps).
```

`module_typing` is WasmCert's specification-level typing judgement for modules,
the inductive relation the paper defines the type system with, not a decision
procedure's opinion of it. The route there is two steps: `validate_module_checked`
lands on `module_type_checker m = Some (imps, exps)`, and WasmCert's own
`module_type_checker_sound` turns that into `module_typing`. The statement is
parametric in WasmCert's `host`; nothing in it depends on the host.

The last three conjuncts are the part an embedder uses. `import_types` and
`export_types` succeed on a validated environment, and the extern types they
report are the ones WebAssembly's type system assigns to the module the bytes
decode to. That is what makes them safe to link against.

**How much of `m` the returned `Module` pins down.** `m` is existential because
validation is a single pass that does not retain function bodies. Everything
else is determined: `Module_Sound.validate_module_parts` states `m` as
`module_of env fs tabs mems datas`, where nine of the ten module fields are a
field of the returned `Env` or `Tail` translated, and `tabs`/`mems` are the
suffix of the env's table and memory index spaces that the import section did
not write. Only `mod_funcs` is genuinely not recoverable. A consumer that needs
the bodies gets them from the hooks (see [The trace](#the-trace)).

### It does not reject a valid module

Two statements, and the difference between them matters.

```coq
Theorem validate_module_complete : forall data m,
  dlen data <= 1073741824 ->
  repr_module_fit (byte_list data) m ->
  module_wasm10 m ->
  exists vm, module_validate_module data = Ok (Ok vm).
```

`module_wasm10` is *itasca's own* statement of module validity, expressed
against the module: the environment sections' conditions, the data segments',
and the code section's typing. Read alone, this theorem is self-referential, and
it is here because it is the induction the next one runs on.

```coq
Theorem validate_module_typechecked : forall data m t_imps t_exps,
  dlen data <= 1073741824 ->
  repr_module_fit (byte_list data) m ->
  module_type_checker m = Some (t_imps, t_exps) ->
  module_1_0 m ->
  exists vm imps exps,
    module_validate_module data = Ok (Ok vm)
    /\ module_import_types vm.(env) = Ok (Ok imps)
    /\ module_export_types vm.(env) = Ok (Ok exps)
    /\ translate_externtypes imps = t_imps
    /\ translate_externtypes exps = t_exps.
```

This is the externally meaningful one: the premise is *WasmCert's* checker, and
the conclusion also says the two extern-type lists the caller had in hand are
the ones itasca reports. What identifies them is `repr_module_det` again: the
bytes decode to one module, so the module itasca decoded is the caller's `m`.

Three qualifications come with it, all visible in the premises.

**`repr_module_fit` is `repr_module` plus two size caps.** Every clause is
identical except the code section's, which additionally requires each entry to
occupy at most `MAX_FUNCTION_BYTES` = 7,654,321 bytes and to declare at most
`MAX_LOCALS` = 50,000 locals. With the file-length premise that is three
implementation caps:

| Cap | Value | Why it exists |
|---|---|---|
| `MAX_MODULE_BYTES` | 1,073,741,824 (2^30) | position arithmetic cannot overflow a 32-bit `usize` |
| `MAX_FUNCTION_BYTES` | 7,654,321 | same, for a body's own cursor |
| `MAX_LOCALS` | 50,000 | a two-byte local declaration can otherwise ask for 4 billion locals |

A module that only exceeds one of these is valid WebAssembly and gets rejected.
These three are the only places itasca is knowingly incomplete against Wasm 1.0.
Note the locals cap is on what a function *declares*, so parameters do not count
against it.

**`module_1_0` is the three restrictions Wasm 2.0 lifted.** A function type
returns at most one value; a module has at most one table and at most one
memory, counting imports. WasmCert's `module` type and type checker are
2.0-shaped, so they admit modules that are not valid 1.0, and rejecting those is
itasca doing its job. `module_1_0` is exactly those three conditions and nothing
else; every other obligation in `module_wasm10` is either one of
`module_type_checker`'s own read backwards or a fact about the encoding that
`repr_module_fit` already carries (`Module_Wasm10.module_wasm10_of_checker` is
that derivation).

**The premise is the checker, not `module_typing`.** See [What is not
proven](#what-is-not-proven).

## Part 2: the decomposed API

`validate_module` is three functions behind one size check:

```rust
let (env, code_pos) = validate_env(data)?;   // everything before the code section
let tail_pos        = validate_code(data, code_pos, &env)?;
let tail            = validate_tail(data, tail_pos, &env)?;
```

Each has a `_with` form taking a visitor, and the code section additionally
exposes `code_section` (read the header) and `validate_code_entry_with`
(validate one function). A compiler drives these itself: it wants the
environment before the bodies, one entry at a time, possibly on other threads,
with operators pushed to it as they are accepted. `src/lib.rs` and the rustdoc on
each function state the same preconditions this section does.

### The two things a caller owes

`validate_module` and `validate_module_with` ask nothing. Every decomposed entry
point asks two things, and neither is enforced by the type system.

**Size.** `data.len() <= MAX_MODULE_BYTES`. `validate_module` checks it once and
then calls the parts, which is why it has no hypothesis; every no-panic and
completeness result about a *part* carries `dlen data <= 1073741824` instead. No
realistic 64-bit host reaches the bound, which makes it easy to treat as a
remark. It is a hypothesis: without it the model's position arithmetic can fail.

**Provenance.** `env` and each position must have come from the earlier parts run
on this same `data`. The theorems enforce this themselves rather than leaving it
to documentation. `Module_Driven.validate_module_of_parts` reads

```coq
Theorem validate_module_of_parts : forall data env code_pos tail_pos tl,
  dlen data <= 1073741824 ->
  module_validate_env data = Ok (Ok (env, code_pos)) ->
  module_validate_code data code_pos env = Ok (Ok tail_pos) ->
  module_validate_tail data tail_pos env = Ok (Ok tl) ->
  module_validate_module data = Ok (Ok {| env := env; tail := tl |}).
```

The hypotheses are equations about `validate_env` and friends on the same
`data`, so a fabricated `Env` does not satisfy them and gets no theorem.
`Module_Driven.validate_module_parts_typed` composes this with
`validate_module_typed`, so three accepting parts inherit the whole of Part 1 on
the same bytes with the same `Module`, rather than having it restated.

`Env`'s fields are public and writable, so nothing stops a caller building one.
Two things then go wrong at once. Soundness is stated relative to the
environment handed over, so a hand-built `Env` earns a true theorem about a
module nobody has. And the code section's no-panic results need `env_small`,
which says every vector in the environment is no longer than the position
reached (each entry cost at least one input byte). `env_small` is
`validate_env`'s postcondition and nothing else's; an `Env` with oversized
vectors can make the model's arithmetic fail.

### Coverage

Every public function has all three results. Given the two obligations above and
the visitor obligations below, no entry point is a gap.

| Function | Returns | Sound | Complete |
|---|---|---|---|
| `validate_module` | `validate_module_no_panic` | `validate_module_repr`, `validate_module_typed` | `validate_module_complete`, `validate_module_typechecked` |
| `validate_module_with` | `validate_module_with_no_panic` | `validate_module_driven` | `validate_module_with_accepts`, `validate_module_with_complete` |
| `validate_env`, `_with` | `validate_env_ok`, `validate_env_with_ok` | `validate_env_sound` | `validate_env_complete` |
| `code_section` | `code_section_ok` | `code_section_sound` | `code_section_complete` |
| `validate_code`, `_with` | `validate_code_ok`, `validate_code_with_ok` | `validate_code_sound`, `validate_code_with_sound`, `validate_code_with_deferred` | `validate_code_complete`, `validate_code_with_complete` |
| `validate_code_entry`, `_with` | `validate_code_entry_ok`, `validate_code_entry_with_ok` | `validate_code_entry_sound`, `validate_code_entry_with_sound` | `validate_code_entry_complete`, `validate_code_entry_with_complete` |
| `validate_tail`, `_with` | `validate_tail_ok`, `validate_tail_with_ok` | `validate_tail_sound` | `validate_tail_complete` |
| `validate_body`, `_with` | `validate_body_no_panic`, `validate_body_with_no_panic` | `validate_body_typed`, `validate_body_with_typed` | `validate_body_complete`, `validate_body_with_complete` |
| `import_types`, `export_types` | `import_types_externs`, `export_types_externs` (both, conditionally) | | |

`validate_module_driven` is the soundness route for the `_with` forms: given
`code_hooks_validate`, a driven run that accepted means `validate_module`
accepts *the same bytes with the same `Module`*, so all of Part 1 applies
unchanged. The `_driven` and `_accepts` pairs exist at every level
(`validate_env_driven`, `validate_code_driven`, `validate_code_entry_driven`,
`validate_tail_driven`, and their mirrors in `Module_Driven.v`), which together
say that driving the walk changes neither the verdict nor the result.

`code_section` reads the code section's header without validating the section.
Its soundness result covers both cases: present means the section is at `pos`,
its declared count matches the function section, and its entries begin just past
that count; absent means nothing at `pos` begins a code section and the module
declared no functions. A consumer that frames the entries itself from
`CodeSection::entries` still owes the check that the extents tile the section
exactly, which `validate_code_with` performs and nothing else does.

**How far a read reaches.** A consumer streaming the code section cannot read a
byte that has not arrived, so before each read it has to know how far that read
can go. `CodeVisitor::on_need_bytes` is where the walk says so, and four lemmas
say the answer covers the read: `read_u32_leb_span` (a `u32` LEB moves the
cursor by at most `MAX_LEB_BYTES`), `read_section_header_span`,
`code_entry_extent_span`, and `code_section_span` (the first entry starts at
most `MAX_CODE_HEADER_BYTES` along). Each is stated against the constant rather
than against 5 or 11, so the theorem is the bound the interface reports. Read
with the matching `_sound` lemma, which says the bytes consumed are exactly
those between the two cursors, the pair turns "the cursor moved at most five"
into "no byte at or past `pos + 5` was read". The per-entry wait is covered by
`code_entry_extent_frames` and `validate_code_entry_with_sound` instead, which
pin the entry's bytes to `[pos, end)`.

### One function body

`validate_body_with(data, env, ctx, v)` is the verified core: `data` is exactly
one body's bytes, locals declarations already stripped and nothing after the
terminating `end`.

```coq
Theorem validate_body_no_panic : forall data env ctx,
  exists r, code_validate_body data env ctx = Ok r.
```

No hypothesis, for any `data`, `env` and `ctx` whatsoever, valid or not.

```coq
Corollary validate_body_typed : forall C0 env ctx data,
  (* C0 is the WasmCert context built from env and ctx: one equation per field *)
  mems_agree env C0 -> locals_agree ctx C0 -> globals_agree env C0 ->
  return_agree ctx C0 -> funcs_agree env C0 -> types_agree env C0 ->
  tables_agree env C0 ->
  length ctx.(results) <= 1 ->
  code_validate_body data env ctx = Ok (Ok ()) ->
  exists es,
    repr_expr (byte_list data) es []
    /\ be_typing (upd_label (context_reverse C0) [results]) es (Tf [] results).
```

`be_typing` is WasmCert's specification-level typing judgement for instruction
sequences. The route is three steps: `validate_body_sound` reaches WasmCert's
decision procedure, `validate_body_checker` restates that in the form WasmCert's
reflection lemma consumes, and `validate_body_typed` applies
`b_e_type_checker_reflects_typing`, which is an if-and-only-if.

The seven `_agree` clauses are not restrictions on the input. Each is a single
equation pinning one field of the WasmCert context `C0` to the corresponding
field of the `env` and `ctx` that were passed, so together they say "`C0` is the
context these arguments describe". `tc_elems`, `tc_datas` and `tc_refs` are left
free, since Wasm 1.0 bodies do not consult them. The one real hypothesis is
`length ctx.results <= 1`, the Wasm 1.0 multi-value restriction.

Note what this does *not* say: nothing requires `env` to be a validated
environment. Body soundness is relative to the environment you pass. Pass a
fabricated one and the conclusion is typing in the context that fabrication
describes, which is a true theorem about no real module.

`validate_body_complete` is the mirror, with the same seven clauses plus
`funcs_wasm10`, `types_wasm10` (at most one result per function type reachable
from `call`/`call_indirect`), the 7,654,321-byte cap, and
`b_e_type_checker_aux ... = true`. For bodies the checker premise and
`be_typing` are interchangeable, because WasmCert's reflection lemma goes both
ways.

`Module_Sound.validate_code_entry_with_sound` is the version a caller can
actually use. It takes a position and an index into the code section, discharges
all seven `_agree` clauses itself, and concludes `repr_code` of the entry's own
bytes plus `code_typed`, which quantifies over the three index spaces bodies do
not use. That is what composes into `validate_module_typed`.

### What a visitor owes

There are three visitor traits, 177 hooks in total: `OpVisitor` (174, being
`on_function_start`, `on_br_table_label`, and one per operator), `ModuleVisitor`
(`on_custom_section`), and `CodeVisitor` (`on_need_bytes`, `on_code_entry`).
Hooks are ordinary unverified Rust. Each obligation below is a named Coq
predicate, and each has a proof that the do-nothing instance satisfies it, which
is why the plain entry points carry no visitor hypothesis.

| Obligation | Predicate | What it buys |
|---|---|---|
| Always return | `hooks_total`, `module_hooks_total`, `code_hooks_total` | no-panic for the `_with` forms |
| Return `Ok` | `hooks_accept`, `module_hooks_accept`, `code_hooks_accept` | completeness for the `_with` forms |
| Validate what you take over | `code_hooks_validate` | soundness when `on_code_entry` is overridden |

The asymmetry is the important part. **No hook can turn a rejection into an
acceptance.** `validate_body_with_typed` holds for every consumer, hostile ones
included, with no hypothesis, because acceptance is decided before a hook is
consulted. What a bad hook can do is refuse a valid body (reported as a
visitor error) or fail to terminate.

`code_hooks_validate` is the one exception to "a hook only reports", and it is
opt-in. `on_code_entry`'s default *is* `validate_code_entry`, so overriding it
means taking over that entry's validation. The obligation is stated as: if your
hook returns `Ok` for `(data, env, index, pos, ..)`, then
`validate_code_entry(data, pos, env, index)` returns `Ok` too.
`Module_Driven.validate_code_entry_driven` is how a compiler discharges it:

```coq
Corollary validate_code_entry_driven : forall V inst data pos env index v q' v',
  module_validate_code_entry_with inst data pos env index v = Ok (Ok q', v') ->
  module_validate_code_entry data pos env index = Ok (Ok q').
```

No hypothesis on the visitor. A consumer whose `on_code_entry` calls
`validate_code_entry_with` on its own `OpVisitor` and returns `Ok` only when
that did has discharged the obligation. Nothing else relates the two functions,
so without this the interface would have a hole exactly where its main use is.

`validate_code_entry_accepts` is its mirror, which discharges
`code_hooks_accept`: the same consumer does not refuse an entry the validator
accepts, provided its own operator hooks do not.

### Validating the entries later

`code_hooks_validate` is a claim about what the hook *returns*, so a consumer
that hands each entry to a compile thread and returns before the thread reports
back cannot satisfy it. That consumer is the main one: the walk frames each
entry and hands it over unvalidated precisely so it can go to another thread.

```coq
Theorem validate_code_with_deferred : forall V inst obs data pos env v q' v',
  code_records inst obs ->
  module_validate_code_with inst data pos env v = Ok (Ok q', v') ->
  entries_validate data env (obs v') ->
  module_validate_code data pos env = Ok (Ok q').
```

The obligation has moved off the hook and onto a list. `code_records inst obs`
is the `CodeVisitor` analogue of `records`: the consumer says `obs` reads its
state as the entries it was handed, as `(index, position)` pairs.
`entries_validate` says every pair on that list validates, which is what the
consumer holds once its last thread finishes rather than when the hook returns.
`entry_recorder` and `entry_recorder_records` supply one visitor that satisfies
`code_records`, so the theorem is not vacuous, and `validate_code_recorded` is
the statement at that visitor with the list as a value.

`validate_module_deferred_typed` composes this with
`validate_module_parts_typed`, so a parallel function compiler reaches the whole
of Part 1 from the state it is actually in when it finishes.

### A module held in three buffers

A streamed module does not arrive as one buffer: the environment is one
allocation, the code section another, the tail a third, and each part is driven
over the region that holds it with a position relative to that region.
`validate_module_of_parts` does not apply to that, because its three hypotheses
are about one `data`.

```coq
Theorem validate_module_regions_typed : forall E C T env cp nc tl,
  module_validate_env E = Ok (Ok (env, cp)) ->
  to_Z cp = to_Z (slice_len E) ->
  module_validate_code C 0 env = Ok (Ok nc) ->
  to_Z nc = to_Z (slice_len C) ->
  module_validate_tail T 0 env = Ok (Ok tl) ->
  begins_code_section (byte_list C) ->
  exists m imps exps,
    repr_module (byte_list E ++ byte_list C ++ byte_list T) m
    /\ ...
    /\ module_typing m (translate_externtypes imps)
                       (translate_externtypes exps).
```

The conclusion is about the concatenation of the three regions' bytes, which is
the module, and there is no fourth slice holding it. Three things make it go
through, and each is something a consumer checks:

- **The regions tile the module.** The two position hypotheses say the
  environment stopped exactly where the split is and the code section's entries
  filled exactly the code region. Without them the regions could overlap or
  leave a gap, and the concatenation would not be what any of them read.
- **The next region begins with the code section.** This is what keeps the
  environment's nine absent cases absent: a section that was absent because its
  region ran out could otherwise reappear at the head of the next one.
  `Spec_Module.repr_padded_app` is the lifting, and the hypothesis is what its
  absent case needs.
- **The tail holds no code section.** Not a hypothesis:
  `Module_Sound.tail_chain_no_code` derives it, since an accepting tail rejects
  any section id but a custom section's or the data section's.

`Module_Driven.validate_module_regions_deferred_typed` is this and the deferred
obligation together, which is the shape a streaming parallel compiler is in.

### The trace

Soundness says the verdict is right. A compiler also needs to know the hooks it
generated code from are the run that earned that verdict.

```coq
Theorem validate_body_with_trace : forall V inst vis vis' C0 env ctx data,
  (* the same seven _agree clauses and results <= 1 *)
  code_validate_body_with inst data env ctx vis = Ok (Ok (), vis') ->
  exists es ops,
    repr_expr (byte_list data) es []
    /\ else_sugar (flat_of es ++ [FO_end]) ops
    /\ repr_ops (byte_list data) ops []
    /\ traced inst vis vis' ops.
```

`ops` is the operator sequence the bytes encode, and `traced` says the consumer
was shown exactly that: none skipped, none repeated, none invented, in byte
order.

Read `traced` carefully, because its shape is the whole story:

```coq
Definition traced inst v v' ops :=
  forall obs pend, records inst obs pend -> pend v = [] ->
    obs v' = obs v ++ ops /\ pend v' = [].
```

It is quantified over the consumer's *own* account of its state. `records inst
obs pend` is the claim that `obs` reads a visitor state as an operator log and
each hook appends the operator its own name claims; `pend` holds a `br_table`'s
labels mid-operator, since those arrive one depth at a time as the loop reads
them (collecting them first would mean a `Vec` bounded only by the byte count).
So the trace theorem is an obligation-discharge shape: prove `records` for your
visitor and you get the trace. A consumer that cannot exhibit such an `obs` gets
nothing from this theorem, and the statement is vacuously true at the
do-nothing visitor.

That is a reasonable burden, since `records` is what a compiler would have to
know about its own emitter in any case. It is still a burden, and it is the one
place in this interface where the strongest guarantee is contingent on work the
consumer does.

**What keeps the tables honest.** A hook per opcode means a table turning an
opcode into a hook, and a table whose rows were off by one would validate just
as well while handing a compiler the wrong instruction. Eight theorems in
`OpIter_Table.v` rule that out. `convert_types_spec` and `binary_types_spec` say
the Rust opcode tables agree with `Spec_Binary.op_spec`, the transcription of
spec 5.4's instruction table. `op_spec_handled` says the dispatch has no gaps:
every opcode `op_spec` assigns a shape to is one the validator handles, either
by an explicit branch or through one of the two tables.
`visit_numeric_names_convert` and its three siblings say that for every row of
both tables, the hook the fan-out picks is the one whose *mnemonic* names the
instruction `op_spec` gives that byte; swap two rows and they stop holding.

`trace_records` is the check that closes the loop. It proves `records` for
`trace_visitor`, a hand-written visitor whose every one of the 174 hooks appends
the instruction its own name claims. `records` has one row per hook *shape*
rather than one per hook, with the two fan-outs a row each, so the 123 numeric
and 23 memory hooks are covered through the four naming theorems above and the
remaining shapes are discharged by computation. Any hook whose name and payload
disagree makes it unprovable. `validate_body_trace` is the trace theorem at that
visitor, where the operator list is an equation rather than a hypothesis.

`Module_Sound.validate_code_entry_with_sound` carries the trace up to the
per-entry entry point a compiler calls: the operators it was shown are the body
of the code entry those bytes encode, with `on_function_start` excluded since it
is not an operator.

### Custom sections

`ModuleVisitor::on_custom_section` reports where a module's custom sections are,
from `validate_env_with` for the ones before the code section and
`validate_tail_with` for the ones after. The decoders already read every one of
them in order to skip it, so this is what they saw and not a second walk.

The report is unverified, and it is outside the verdict. A custom section is not
part of the module a binary denotes, and `Spec_Module.v` reads the format's
customs as padding, so the worst a wrong answer here can do is mislead a
consumer about where a name lives. No theorem says the ranges reported are the
custom sections the format says are there, and there is no `records`-style trace
obligation for `ModuleVisitor` to make one out of.

### `import_types` and `export_types`

`Module_Externs.import_types_externs` and `export_types_externs` say these
return `Ok`, with the extern types the format assigns, provided the
environment's descriptors are in range. That premise is `validate_env`'s
postcondition and is discharged inside `validate_module_typed`. On a hand-built
`Env` they still cannot panic (both bounds-check in Rust and return `Err`), but
no theorem says so.

## What is not proven

**Module completeness against `module_typing` rather than the checker.**
`validate_module_typechecked`'s premise is WasmCert's *decision procedure*
saying yes, not its typing judgement `module_typing`. WasmCert proves the module
checker sound and never proves it complete, so accepting-by-the-checker is the
stronger requirement: a module that `module_typing` admits but the checker
rejects would fall outside the theorem. Function bodies do not have this gap,
because there WasmCert's reflection lemma is an if-and-only-if.

**The custom-section report.** As above.

**Error messages and byte offsets.** `Error` carries no position, and nothing is
proven about which error a rejection produces, only that it is a rejection.

**An embedder's own implementation caps.** This crate deliberately enforces none
of the caps a real engine needs (counts of types, functions, imports, exports,
globals, segments, parameters, `br_table` entries, and locals counted with
parameters). A cap can only ever reject, so importing one could not make the
validator unsound, but each would become another hypothesis on completeness for
a limit the specification does not have. An embedder whose data structures
assert on those bounds has to enforce them itself, on its own side, and nothing
here helps it do so.

**Anything about execution.** This is a validator. Nothing here says a validated
module runs correctly, and WasmCert's type-soundness results are not chained to.

## The trust base

**WasmCert-Coq is a faithful formalisation of WebAssembly.** Everything above
reduces "well typed" to WasmCert's `module_typing` and `be_typing`.

**Our transcription of the binary format is right.** `theories/Spec_Binary.v`
for instructions, `Spec_Expr.v` for expressions and the `else` a bare `if`
elides, `Spec_Module.v` for the module around them. WasmCert cannot supply
these: its `binary_format_spec.v` declares `repr_module` as an inductive with no
constructors at all, and its parser has no correctness theorem, so agreeing with
it would only mean agreeing with unverified code. Ours is a hand transcription
of the specification's tables, one-line rules with no clever reasoning.
`repr_module_det`, `repr_expr_det` and `repr_ops_det` are the internal audit of
it: an ambiguous transcription is one where two modules claim the same bytes,
and those three rule that out.

**A 1.0 module is the 2.0 module we say it is.** WasmCert's `module` type is
2.0-shaped, so `Spec_Module.v` has to say which 2.0 value a 1.0 binary denotes,
and in two places the answer is a transform rather than a copy: an element
segment's vector of function indices becomes one `ref.func` expression each, and
a data segment's memory index becomes part of its mode.

**`theories/Translate.v` maps itasca's types onto WasmCert's.** Definitions
only, one line per case, no proofs: `ValueType::I32` is `T_num T_i32`, a table
type's element type is `T_funcref`, type lists are reversed because itasca's
stacks grow rightward and WasmCert's leftward. A wrong line here would make the
theorems true statements about the wrong types. It is short enough to read in
one sitting, and the module-level proofs cross-check most of it against
`Spec_Module.v`, which independently maps bytes to WasmCert types.

**Charon and Aeneas translate Rust to Coq faithfully.** If the translation is
wrong, the proofs are about a program other than the one that ships. The
extraction is committed, so it can drift from `src/`; `just extract` regenerates
it and the result should differ only in `Source:` line-number comments.

**Aeneas's `loop`, and its model of the Rust standard library.** `just trust`
prints the axiom count per theorem. The strongest results reach 60. The rise
from 52 is the cost of using fixed Rust arrays for the three inline stacks:
Aeneas represents an array as a length-indexed list, but leaves construction,
indexing and update as primitive operations whose intended list semantics the
project states explicitly. This is the same trust pattern already used for
`Vec` and slices, rather than a new kind of kernel bypass.

For the strongest completeness results, the 60 assumptions fall into four
groups:

- **20** in `theories/Aeneas_Specs.v`. These describe what Rust operations do:
  what `Vec::pop` returns, what indexing a slice gives you, what a sub-slice
  contains, what array indexing and update do, what two of our derived
  `PartialEq` impls do, and `loop_unfold`. Some soundness results reach 19
  rather than all 20.
- **10** of the 13 in `theories/Itasca_FunsExternal.v`, which is hand-written
  despite the name: what Aeneas emits for library functions it does not
  translate, plus `loop` itself. The other three are defined and unreached.
- **25** from Aeneas's own `Primitives.v`. These are the operations the first
  group constrains rather than descriptions of them: `slice_index_usize`,
  `slice_len`, `array_repeat`, `array_index_usize`, the two array update
  operations, `alloc_vec_Vec_index`, the `core_slice_index_*` family, and the
  six `usize`/`isize` bound constants. Trusting these is trusting that Aeneas's
  encoding of Rust's scalar, collection and slice primitives is the right one,
  which is a distinct assumption from trusting that it translated our functions
  faithfully.
- **5** logical/classical axioms: `classic`, two
  `ClassicalDedekindReals` decidability axioms,
  `functional_extensionality_dep`, and `proof_irrelevance`. The first four are
  inherited from WasmCert's use of the CompCert floating-point library;
  `proof_irrelevance` lets the proofs identify two arrays with equal element
  lists despite their length proofs. `validate_module_no_panic` reaches 56 and
  uses only `proof_irrelevance` from this group.

`loop` and `loop_unfold` are the load-bearing pair. Every claim of termination
is relative to them.

**Your hooks, if you use a `_with` form.** The obligations in [What a visitor
owes](#what-a-visitor-owes) are assumptions about code this repository does not
contain. `hooks_total` is discharged by not panicking and not looping;
`hooks_accept` by returning `Ok`; `code_hooks_validate` by
`validate_code_entry_driven`.

**Coq's kernel.** Standard for work of this kind. There are no `Admitted`
proofs, no `Axiom` outside the two files named above and Aeneas's `Primitives.v`,
and no `Unset Guard Checking` or `Unset Positivity Checking` anywhere;
`just extract-check` fails the build if the extraction acquires one, and
`just trust` reports zero bypasses for every theorem it lists.

## What corroborates but does not prove

None of this is part of the argument. It is what catches the mistakes the
argument cannot make: a wrong transcription of the format, a wrong `Translate.v`
line, a wrong Aeneas translation.

- **295 Rust tests**, including 143 that walk the streaming validator operator
  by operator and 12 on which hook fires with what.
- **2,419 binaries** extracted from the W3C spec test suite at the `wg-1.0` tag
  (778 expected-valid, 1,641 expected-invalid), each run through
  `validate_module` and cross-checked against `wasmparser` configured for
  exactly the Wasm 1.0 feature set. One known divergence, where `wasmparser`
  disagrees with the suite and itasca matches the suite. A second test compares
  the reported import and export types against `wasmparser`'s.
- **Two `cargo-fuzz` targets**, both differential against `wasmparser`.
  `raw_bytes` checks the soundness direction on unstructured input (itasca must
  never accept what `wasmparser` rejects; the converse would fire on the
  implementation caps). `wasm1_smith` checks the completeness direction, with
  `wasm-smith` restricted to the Wasm 1.0 feature set and kept under the caps.

## Checking it yourself

```bash
just prove             # recompile every theory
just trust             # axioms and kernel bypasses per theorem
just assumptions Module_Typing validate_module_typed
just extract           # regenerate the Coq model from src/
just extract-check     # the extraction has no kernel bypasses
just externals-check   # the hand-written externals against what Aeneas asks for
cargo test
```
