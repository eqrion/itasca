# Development

## Layout

```
src/
  lib.rs              Public API: validate_module()
  module.rs           Fused decode + validate, split into environment, code, tail.
                      `validate_code_entry_with` is the per-function entry point.
                      Env: everything the binary declares before the code section
  types.rs            Value and external types, mirrors WasmCert-Coq datatypes.v
  limits.rs           Every numeric bound the validator enforces
  reader.rs           Byte-level reads over (data, pos): bounds, LEB128, floats.
                      Private: not a validation routine
  code.rs             Streaming function-body decode + validate, the verified
                      core, and the push interface: one hook per opcode, and
                      its tables
  error.rs            Error, OpError and VisitError

theories/
  Aeneas_Specs.v      Aeneas primitive specs + scalar/list helpers
  Translate.v         Extracted types -> WasmCert types
  Spec_Binary.v       The W3C instruction format transcription. Trust item
  Spec_Expr.v         Flattening and the `else` a bare `if` elides. Trust item
  Spec_Module.v       The W3C module format transcription (spec 5.5). Trust item
  OpIter_Visit.v      What a consumer's hooks have to satisfy
  OpIter_Driven.v     One consumer's run of a body is another's
  OpIter_*.v          The streaming validator's proof
  Module_NoPanic.v    The module decoder cannot panic or diverge
  Module_Sound.v      The module decoder reads what Spec_Module.v says
  Module_Driven.v     What a consumer that drives the walk itself gets: the
                      entry-level erasure, the mirror of every _driven lemma,
                      and validate_module read as three parts
  Itasca_Types.v      Generated by Aeneas; do not edit
  Itasca_Funs.v       Generated by Aeneas; do not edit
  Itasca_FunsExternal.v
                      Hand-written models of what Aeneas leaves opaque. Aeneas
                      emits a *_Template.v naming what it needs; `just
                      externals-check` compares the two

tests/
  wasm_tests.rs       Module decode + validate, end to end
  code_tests.rs       The streaming validator, operator by operator. The unit
                      tests for reader.rs and the two opcode tables live beside
                      the code, since neither is public any more
  visit_tests.rs      The push interface: which hook fires, with what
  spec_tests.rs       Differential test against the Wasm 1.0 spec test suite
  spec/               Binaries extracted from tests/third_party/wasm-spec
  support/            Shared code between examples/wast_extract.rs and fuzz/
  third_party/        wasm-spec submodule, pinned to the wg-1.0 tag

examples/
  wast_extract.rs     Regenerates tests/spec/ from tests/third_party/wasm-spec

fuzz/                 cargo-fuzz targets, differential against wasmparser

_CoqProject           Coq load path and file list; Makefile.coq is generated
                      from it by coq_makefile
patches/              Local fixes to the vendored submodules
```

## The pipeline

```
Rust source
  |  Charon
  v
LLBC (itasca.llbc)
  |  Aeneas
  v
Coq functional model (theories/Itasca_Funs.v)
  |  manual theories (theories/OpIter_*.v, theories/Module_*.v)
  v
Proof against WasmCert-Coq's b_e_type_checker, which
type_checker_reflects_typing.v already relates to be_typing
```

Changing the Rust means re-extracting and re-proving. The generated theories are
committed, so they have to stay in sync with `src/`.

Adding a hook to `OpVisitor` means three mechanical blocks have to grow with it,
all of them one entry per hook in the order the trait declares them:
`hooks_total` and `hooks_accept` in `OpIter_Visit.v`, and `trace_visitor` in
`OpIter_Table.v`. A hook that is not in either fan-out table records nothing in
`trace_visitor`; one that is records the instruction its mnemonic names, read
off the mnemonic and never off the opcode, or the four theorems there stop
being a check on the tables.

A hook with a *new dispatch shape* -- one the four `visit_hook`/`visit_wrap*`
forms in `OpIter_Visit.v` do not cover -- also needs a branch in
`OpIter_Driven.step_transfer`. One that reuses a shape needs nothing there,
because that proof is driven by the shape and not by the hook.

A hook that fires once per operator also needs a row in `records`
(`OpIter_Visit.v`), which is what a consumer claims about its own state and
what `trace_records` has to discharge. `records` is one row per hook *shape*
rather than per hook: the two fan-outs are one row each, and a new
`i32`-flavoured arithmetic hook needs no row at all. Only a hook with a new
signature, or one that is not an operator (`on_function_start` is the example),
adds one.

```bash
cargo test              # Rust tests
just extract            # re-extract after changing the Rust
just prove              # compile all theories
just check FILE         # one theory file plus its dependencies
just profile FILE       # slowest sentences in a file
just trust              # assumptions each theorem depends on
just extract-check      # the extraction must have no kernel bypasses
just externals-check    # Itasca_FunsExternal.v against what Aeneas asks for
just scratch            # iterate on one lemma in theories/Scratch.v (gitignored)
```

## Toolchain setup

Needs [opam](https://opam.ocaml.org/), Coq via opam, and the Aeneas toolchain
(which builds Charon itself).

```bash
brew install opam
opam init --auto-setup --bare

opam switch create aeneas 5.2.0
eval $(opam env --switch=aeneas)
brew install pkgconf
opam install coq -y --confirm-level=unsafe-yes

git submodule update --init

cd ./vendor/aeneas
brew install make
gmake setup-charon    # builds Charon at the pinned commit
opam install ppx_deriving visitors easy_logging zarith yojson \
  core_unix ocamlgraph unionFind menhir domainslib progress -y \
  --confirm-level=unsafe-yes
cd src && dune build
```

Two opam switches are in play: `aeneas` builds the extraction toolchain,
`wasmcert` holds Coq and the proofs. The Makefile knows about both.

### Vendored dependencies

WasmCert-Coq and Aeneas live in `vendor/` as submodules pinned to exact upstream
commits. `tests/third_party/wasm-spec` is a third submodule, pinned to the
`wg-1.0` tag (the last point before bulk memory, reference types and other
post-MVP proposals were merged into `test/core`); it feeds the differential
tests and needs no patch. WasmCert-Coq and Aeneas each need a small local fix,
applied from `patches/` by the Makefile before building. Neither patch touches
a theory file, so neither affects the trust base:

| Patch | What it does |
| --- | --- |
| `wasmcert-coq-8.18.patch` | Relaxes WasmCert-Coq's `coq < 8.18~` bound; the formalisation builds unchanged on 8.18 |
| `aeneas-coq-tuple-binder.patch` | Fixes Aeneas's Coq backend to emit `fun '((a, b) : T) =>`; the form it emits today does not parse in any Coq |
| `aeneas-coq-slice-index-clash.patch` | Drops two wrong `extract_name` overrides that gave `SliceIndex<usize>::index` the name Coq's `Primitives.v` uses for the generic `Index` wrapper. Using both `s[i]` and `&s[a..b]` in one crate hit the clash and Aeneas refused to name either |

The patches are applied in place, so both submodules are expected to have a
dirty working tree. `.gitmodules` sets `ignore = dirty` so git does not report
it.

## Constraints on the Rust

### The Aeneas subset

Aeneas translates a subset of Rust. Code outside it either fails to translate or
produces a Coq model that will not typecheck. Nothing is marked opaque any more,
so all of `src/` has to stay inside it: safe Rust, no raw pointers, full stop.

- Safe Rust only, no `unsafe`
- No struct holds a borrow: the byte cursor is `data` plus `pos`, threaded
  explicitly
- No labeled `break`/`continue`, no closures, no iterator chains
- No `return` inside nested loops; inner loops go in separate functions
- Explicit loop counters instead of iterators
- No bitwise operators. `scalar_and`/`scalar_or`/`scalar_shl` are unspecified
  axioms in Aeneas's `Primitives.v`, so LEB128 decoding uses division and
  remainder, which have real definitions over `Z`
- `core` + `alloc::vec::Vec` only. No `String`: `core::str::from_utf8` is not
  translatable, so names are `Vec<u8>` and `module.rs` validates the UTF-8
  itself
- Prefer an `end` position threaded alongside `pos` to a sub-slice. `&data[a..b]`
  does translate, but it goes through `core_slice_index_SliceIndexRangeUsizeSlice_get`,
  which is an axiom, so every use adds one to the trust base of anything that
  reaches it. `validate_code_entry` uses one because the body's exact extent is
  part of a theorem; nothing else should need to
- No `.clone()`. `Charon.toml` excludes the `Clone` and `Copy` impls from the
  LLBC, so a clone anywhere fails to translate. Copy what you need with an
  explicit loop, as `module::copy_value_types` does

### Line numbers are part of the extraction

`Itasca_Funs.v` records a source line per definition, so inserting a line
anywhere in `src/` rewrites every `Source:` comment below it. That is why
`code.rs` re-exports its two opcode tables at the bottom of the file rather
than next to them: the change had to add no line above anything. A diff to `theories/`
that is only `Source:` comments is a diff to nothing, but it is still noise in a
review, so avoid causing one.

### SpiderMonkey's implementation caps are SpiderMonkey's

`WasmConstants.h` enforces a family of caps this crate has no analogue for:
`MaxTypes`, `MaxFuncs`, `MaxImports`, `MaxExports`, `MaxGlobals`,
`MaxDataSegments`, `MaxElemSegments`, `MaxParams`, `MaxBrTableElems`. It also
counts a function's parameters against `MaxLocals`, where `MAX_LOCALS` here caps
only what the function declares.

Do not import any of them. A cap only ever rejects, so none can make the
validator unsound, but each becomes another hypothesis on
`validate_module_complete`, and none is a specification requirement. The frame
version of `MaxLocals` is the worst of them: the bound would become a joint
condition on a function's type and its body, which means carrying it through
`code_typed_at` and `repr_module_fit` to the top, for a limit the specification
does not have and this crate does not need.

They have to be enforced on SpiderMonkey's side in any case.
`WasmTypeDef.h`'s `FuncType` has a `MOZ_RELEASE_ASSERT(args_.length() <=
MaxParams)`, so a validator that let a wider type through would crash it rather
than reject it. SpiderMonkey already walks the decoded environment to build
`CodeMetadata`, and that walk is where its own limits go.

### Errors carry no byte position, and putting one in them is expensive

SpiderMonkey writes "at offset N" into its wasm error messages, and `Error` has
nowhere to put one. This looks like a small gap and is not.

A position cannot come from a `From` impl, and `impl From<OpError> for Error` is
what every `?` in a decoder uses. So threading a position through would mean
replacing all 312 `?`s in `module.rs`, `code.rs` and `reader.rs` with explicit
matches, and reshaping the 200-odd `try_err`-style steps in the proofs that walk
their error arms. That is a great deal of churn for error strings, which both the
core specification and the web embedding leave unspecified.

The part that matters most is available without any of it.
`veriwasm_validate_code_entry` reports the offset of the operator a rejected body
stopped at, which is what a compiler names in a diagnostic; the shim knows it
because the last hook to fire reported an operator that was accepted. Module-level
rejections are bracketed to the entry point's `pos` and no closer.

### Adding a module hook

`ModuleVisitor` is the operator visitor one level up: it is what `validate_env`
and `validate_tail` report to, and both take the same one, so a consumer hears
about a module's sections in module order without caring which side of the code
section they came from. A new hook there costs three things here, plus
whatever a C ABI built on top of this trait needs to grow to match --
SpiderMonkey's `veriwasm_glue` is one such consumer, and growing its vtable is
its own concern, not this crate's:

- a method with a do-nothing default on the trait, at the bottom of `module.rs`
- a conjunct in `module_hooks_total` (`Module_NoPanic.v`) and in
  `module_hooks_accept` (`Module_Complete.v`), and a line in each of their nop
  lemmas
- the `_with_loop` proofs that pass the hook: each destructs the call and
  threads the visitor state, and the nop corollary below it needs nothing

A code hook costs the same three, against `code_hooks_total`
(`Module_NoPanic.v`), `code_hooks_accept` and `code_hooks_validate`
(`Module_Complete.v`, `Module_Sound.v`), plus a fourth: the loop transfer
lemmas in `Module_Driven.v` destruct every hook call twice, once in the run
they are given and once in the run they are building.

Note that `code_hooks_total` is indexed by the bytes and the environment rather
than closed: `on_code_entry`'s default
*is* `validate_code_entry`, which is total only where the environment is small
and the position is inside the input. It is the one place the `hooks_total`
pattern from `OpIter_Visit` does not copy verbatim.

Prefer a hook to a field on `Env`. `chain_from` pins a decoded `Env` field for
field and `chain_custom` says a custom section leaves it alone, so anything the
walk writes and no theorem mentions has to be erased again before the chain can
speak. TRUST.md has the long version.

One thing to keep in mind for any C ABI built on this: the values of the enums
this crate exposes are SpiderMonkey's, which are the binary format's, so
handing one across is an identity for a consumer that matches them up that
way -- worth a test on whichever side does the matching. And an entry point
should abort on a null pointer or an out-of-range index rather than report a
rejection or invent a value, because a verdict or a value that came from a
caller's mistake would be indistinguishable from a real one.
